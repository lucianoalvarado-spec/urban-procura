## Despliegue

Producción: **https://urban-procura.vercel.app** — proyecto Vercel `urban-procura` bajo el team `urban-procura`, conectado por Git al repo GitHub `lucianoalvarado-spec/urban-procura` (rama `main`). Cada `git push` a `main` dispara un build y deploy automático en la infraestructura de Vercel.

**No usar `vercel deploy`/`netlify deploy` ejecutados directamente desde esta máquina Windows** para desplegar — es la causa raíz de una sesión entera de debugging: el build local en Windows sube a Vercel con una carpeta "src/" duplicada de forma inconsistente y, más grave, hace que `vercel build`/el plugin de Next.js de Netlify produzcan salidas sin rutas registradas (`builds: []`, `NOT_FOUND` en todo, o "Failed publishing static content" en Netlify) — confirmado como un problema específico de Windows (reportado también por terceros en el foro de Netlify). La única forma que funcionó de manera confiable fue conectar Vercel al repo de GitHub (Vercel > Import Git Repository, tras conectar la cuenta de GitHub en vercel.com/account/login-connections) para que el build corra en los servidores Linux de Vercel. Simplemente: **`git push`, no `vercel deploy` local — y solo cuando el usuario lo pida ese turno** (ver nota de flujo de trabajo arriba).

En producción, el Explorador/Dashboard/landing llegaron a degradar a mock incluso cuando la fuente respondía bien server-to-server. Dos rondas de mitigación en sesiones distintas:

1. `export const preferredRegion = "gru1"` (São Paulo, la región Vercel más cercana a Perú) en `explorador/page.tsx`, `dashboard/page.tsx`, `oportunidades/page.tsx`, `procesos/[id]/page.tsx` y `(marketing)/page.tsx`, más subir los timeouts de fetch de `lib/data/live/oece.ts` de 8s a 15s.
2. Se descubrió que **ninguna ruta tenía `maxDuration` configurado** — corrían bajo el límite por defecto de las funciones serverless de Vercel, más corto que los timeouts internos de 15s, así que la plataforma mataba la función a mitad del fetch antes de que el `AbortController` interno llegara a dispararse. Además, `/api/procesos/buscar`, `/api/entidades/buscar` y las tres rutas `/api/rnp*` corren como sus propias funciones serverless y **no heredan** la config de la página que las invoca — no tenían `preferredRegion` ni `maxDuration` en absoluto. Se agregó `maxDuration = 30` (45 en `dashboard/page.tsx`, que pagina el catálogo completo de 3,316 entidades) a las páginas, y `preferredRegion = "gru1"` + `maxDuration = 30` a las cinco rutas API. También se le agregó timeout (15s, antes no tenía ninguno) a `obtenerProcesosPorRegionLive`.

**Desplegado y el problema seguía sin resolverse.** Confirmado con el commit status de GitHub que el deploy terminó en `"success"`. Se hizo una prueba diagnóstica adicional: `curl` directo a `https://contratacionesabiertas.oece.gob.pe/api/v1/indexCountData?format=json` desde esta máquina Windows respondió `200 OK` en ~0.5s, y un fetch desde la infraestructura cloud de Anthropic (herramienta WebFetch) también trajo el JSON completo sin problema — pero las funciones de Vercel (probadas con hasta 45s de `maxDuration`, en `gru1`) siguen fallando de forma consistente en cada deploy. Esto apuntaba a que el timeout/latencia nunca fue la causa real.

**Causa confirmada (sesión posterior):** se agregó temporalmente `/api/debug/oece` (ya eliminado), una ruta que en vez de tragarse el error devolvía el resultado crudo del fetch. Desplegada y consultada con `curl` directo a producción, la respuesta fue:

```json
{"ok":false,"status":403,"statusText":"Forbidden","headers":{"connection":"keep-alive","content-length":"69"},"bodyPreview":"{\"code\":\"403\",\"message\":\"Forbidden\",\"RequestId\":\"${http.request.id}\"}","tiempoMs":269,"region":"iad1"}
```

Es decir: **403 Forbidden en ~270-600ms** (nunca un timeout) — el cuerpo `{"code":"403","message":"Forbidden","RequestId":"${http.request.id}"}` (con la variable de plantilla sin resolver, sin header `Content-Type` ni ningún otro header propio de la app) es la firma característica de un bloqueo a nivel de WAF/API Gateway, no una respuesta de la aplicación real del OECE. Se probaron dos mitigaciones más antes de concluir el diagnóstico, ninguna cambió el resultado:
- **Edge Runtime** (`export const runtime = "edge"`) en vez de Node/Lambda: mismo 403, mismo cuerpo — solo cambió la región reportada (`iad1` con Node → `gru1` con Edge), descartando que el bloqueo sea específico de las IPs de AWS Lambda.
- **User-Agent de navegador real** (Chrome/Windows) en vez del default del fetch: mismo 403.

**Conclusión: el OECE bloquea el tráfico de la infraestructura de Vercel a nivel de red/WAF** (probablemente una regla que bloquea rangos de IP de proveedores cloud/hosting conocidos — patrón común y ya sospechado, ahora confirmado con la respuesta real del servidor) — **no es un bug de este código, ni de timeout, ni de región, ni de runtime, ni de User-Agent.**

**Primer intento — relay en Cloudflare Workers (`cloudflare-relay/`): NO funcionó.** La teoría era razonable (correr en la red de Cloudflare, no en la de Vercel/AWS), y el Worker respondía perfecto cuando se lo llamaba directo con `curl` desde esta máquina — pero cuando **Vercel** lo llamaba, seguía recibiendo el mismo 403 del OECE, consistente en 8 intentos con pausas, incluso con `[placement] mode = "smart"` en `wrangler.toml` (que mueve la ejecución del Worker cerca del origen al que llama, en este caso el OECE en Perú). Conclusión: Cloudflare Workers no tiene una IP de salida fija — ejecuta en el punto de presencia (PoP) más cercano a quien lo llama, y el/los PoP(s) que atienden a Vercel (EEUU/Brasil) resultaron estar tan bloqueados por el WAF del OECE como la red de Vercel misma. El código y el Worker se dejaron en el repo (`cloudflare-relay/`) por si se quiere retomar, pero **no es la solución activa**.

**Solución que sí funciona: relay local vía Cloudflare Tunnel** (`local-relay/`, ver su propio README). Un servidor Node plano (`server.js`, sin dependencias) corre en la propia PC del usuario en Perú — la misma IP residencial/de oficina que ya se había confirmado que el OECE NO bloquea — y Cloudflare Tunnel (`cloudflared tunnel --url http://localhost:8787`) lo expone con una URL pública, sin abrir puertos en el router. A diferencia del Worker, acá el fetch al OECE lo hace literalmente la PC del usuario, no la red de Cloudflare, así que no importa desde dónde Vercel llame a la URL del túnel — el tráfico hacia el OECE sale siempre por la misma IP ya confirmada como buena.

- `lib/data/live/oece.ts` y `src/app/api/entidades/buscar/route.ts` arman `BASE_URL`/`BASE` condicionalmente: si `OECE_RELAY_URL` está seteada, pasan por `${OECE_RELAY_URL}/proxy/v1` (agregando el header `x-relay-token` desde `OECE_RELAY_TOKEN`); si no, pegan directo al OECE como antes — el desarrollo local sigue sin depender de ningún relay.
- **Usando un Quick Tunnel** (`cloudflared tunnel --url ...`, sin dominio propio) — la URL es **temporal**: cambia cada vez que se reinicia `cloudflared`. Cuando eso pase, hay que actualizar `OECE_RELAY_URL` en Vercel con la URL nueva y hacer Redeploy. Si se quiere una URL fija (túnel con nombre), hace falta que el usuario tenga o agregue un dominio a su cuenta de Cloudflare — pendiente, no configurado todavía.
- **Depende de que la PC del usuario esté prendida** con `node server.js` (`local-relay/`) y `cloudflared tunnel` corriendo — si se apaga o se cierran esas terminales, la app degrada visiblemente a datos de muestra (no se rompe, solo deja de tener datos en vivo). No hay todavía nada que lo mantenga corriendo automáticamente (ej. como servicio de Windows / Task Scheduler) — pendiente si se quiere que sobreviva a reinicios sin intervención manual.
- **No se tocaron las rutas del RNP** (`eap.oece.gob.pe`, `eap.osce.gob.pe`) — nunca se confirmó que estén bloqueadas (el diagnóstico solo probó `contratacionesabiertas.oece.gob.pe`), así que no pasan por ningún relay.
- Verificado end-to-end en producción: Explorador (60/60 procesos reales), landing (contadores reales del OECE) y Dashboard (mapa de regiones con datos reales) — los tres mostrando datos en vivo tras apuntar `OECE_RELAY_URL` al túnel.

- `h1`/`h2`/`h3` usan `var(--font-heading)` (Barlow Condensed) por una regla CSS global — no hace falta agregar la clase a mano en cada título; para no-headings que necesiten la tipografía condensada (ej. `Badge`) se usa la clase `.font-heading`.
- **Sidebar y Topbar rediseñados a tema navy oscuro** (`components/layout/sidebar.tsx`, `topbar.tsx`) al estilo "title block" del mockup (header tipo plano de ingeniería, borde inferior naranja de 3px) — son los únicos componentes de layout que necesitaron colores hardcodeados fuera de las variables (`#0F2A3E`, `#9FB4C2`, etc.) porque el resto de la app asume fondo claro.
- **No se tocó color por color cada página individual** — los textos `text-slate-500/600/400` (escala gris de Tailwind, no ligada a las variables custom) se dejaron como están a propósito, es una decisión de alcance: siguen leyéndose bien como texto secundario sobre el nuevo fondo "paper" y tocar cada archivo habría sido desproporcionado frente al cambio de alto impacto que ya logran las variables + layout + tipografía. ## Decisiones de arquitectura

- **Capa de datos como adaptador reemplazable** (`src/lib/data/provider.ts`): toda la UI llama a `listProcesos`, `getProceso`, `getProveedor`, `obtenerEstadisticas`, `obtenerProcesosPorRegion`, nunca importa los fixtures ni `lib/data/live/*` directamente. `listProcesos`/`getProceso` intentan el OECE en vivo primero (`lib/data/live/oece.ts`) y caen a los fixtures mock si falla — cada `Proceso` devuelto queda marcado `fuente: "mock" | "live"` (nunca se degrada en silencio: la UI siempre puede distinguir uno de otro). `getDataMode()` sigue devolviendo `"mock"` a propósito — ya no describe fielmente el estado real (los procesos pueden ser live), quedó solo como bandera para el perfil/preferencias que sí son 100% mock; no te fíes de ella para saber si el Explorador está en vivo, mira `proceso.fuente`. `obtenerEstadisticas`/`obtenerProcesosPorRegion` **no tienen fallback mock a propósito** (son cifras institucionales reales, no procesos de muestra) — si la fuente falla, la sección correspondiente simplemente no se renderiza en vez de inventar un número.
- **Fixtures** en `src/lib/data/mock/` (`procesos.ts`, `proveedor.ts`) — 14 procesos y 1 proveedor demo con datos peruanos realistas pero ficticios. Sirven de fallback cuando el OECE no responde, y de base para el perfil demo cuando nadie se ha registrado. `listEntidades()`/`listRegiones()` (que derivaban de estos fixtures) se eliminaron de `provider.ts` — ya no se usan en ningún lado, los pickers de Región/Entidad ahora usan la lista completa real (`REGIONES` en `constants.ts`) o el catálogo live (`/api/entidades/buscar`).
- **Matching** (`src/lib/data/matching.ts`): heurística explicable por pesos (región, rubro, monto, entidad, palabra clave, tipo de procedimiento, experiencia mínima). Devuelve score + nivel + listas de coincidencias/faltantes explícitas, no solo un número.
- **Estado del lado del cliente** vive en `src/lib/state/`, respaldado por un store minimalista sobre `localStorage` (`local-store.ts`, `createLocalStorageStore`) leído con `useSyncExternalStore` (evita el error de lint `react-hooks/set-state-in-effect` y es hydration-safe: el snapshot de servidor es siempre el default).
  - `proveedor-context.tsx` (`ProveedorProvider`/`useProveedor`): combina `proveedorMock` + `datosEmpresa` (store) + `preferencias` (store) + `plan` (store) en un único `proveedor`. El orden del spread importa: `{...proveedorMock, ...datosEmpresa, preferencias, plan}` — cualquier campo presente en `datosEmpresa` reemplaza al mock; los campos ausentes siguen mostrando el demo (Vientos del Sur) para no romper la experiencia de "solo estoy explorando" sin haberse registrado.
  - `empresa-store.ts` (`useDatosEmpresa`/`setDatosEmpresa`/`updateDatosEmpresa`): `Partial<Proveedor>` persistido, poblado por `/registro` (RUC, razón social, RNP, correo, teléfono, y arrays de experiencia/personal clave/equipamiento/documentos **vacíos explícitamente**, para no heredar los datos de muestra) y editado luego desde `/perfil` vía `actualizarDatosEmpresa` (expuesto por `useProveedor()`).
  - `plan-store.ts` (`usePlan`/`setPlan`): independiente de `ProveedorProvider` a propósito, porque `/registro` vive fuera del grupo `(app)` y necesita escribir el plan sin montar ese contexto.
  - `crm-context.tsx`: estado de seguimiento (`EstadoOportunidad`) por proceso, usado en Explorador, Ficha y `/oportunidades`.
  - `reclamos-store.ts` (`useReclamos`/`registrarReclamo`): reclamos/quejas del Libro de Reclamaciones, numerados correlativamente (`RQ-000001...`). Igual que todo lo demás, sin backend: queda en localStorage del navegador de quien lo llena, no llega a ningún lado real todavía.
  - Sin backend todavía: esto es persistencia local del navegador, no multiusuario. Cuando exista backend, estos stores deben pasar a leer/escribir vía API en lugar de `localStorage`.
- **Adjuntos de archivos reales** (`components/perfil/adjuntos-field.tsx`, `AdjuntosField`): sin backend/S3 todavía, así que un archivo adjuntado se lee con `FileReader.readAsDataURL` y se guarda como data URL dentro del registro (localStorage) — funciona de verdad (se puede descargar/ver después) pero con tope de 3 MB por archivo por las limitaciones de tamaño de localStorage. Usado en Personal clave y Equipamiento (`documentos?: DocumentoAdjunto[]` en `lib/data/types.ts`); antes de esto **ninguno de los dos** tenía adjuntar archivos real (Personal clave solo tenía un checkbox "CV adjunto", Equipamiento no tenía nada).
- **Patrón de páginas**: `app/**/page.tsx` es Server Component, hace `await listProcesos()`/etc. y pasa los datos a un Client Component (`*-client.tsx`) que consume los contexts y calcula matching. Mantener este patrón al agregar páginas nuevas.
- **Nav y mapa de módulos**: `src/lib/nav.ts` es la fuente de verdad de qué módulos existen, en qué plan comercial están (`free`/`basico`/`profesional`/`premium`) y cuáles son placeholder (`proximamente`). Los placeholders usan `components/proximamente/proximamente.tsx`.
- **Dos grupos de rutas**: `src/app/(marketing)/` es público (landing `/`, `/login`, `/registro`, `/legal`, `/terminos`, `/libro-reclamaciones`, `/blog`) con su propio layout (`components/marketing/*`, sin sidebar). `src/app/(app)/` es el dashboard interno (`/dashboard`, `/explorador`, `/procesos/[id]`, `/perfil`, `/oportunidades`, módulos "próximamente") y monta `ProveedorProvider`/`CrmProvider` en su propio `layout.tsx`. El `layout.tsx` raíz solo pone `<html>/<body>` y fuentes — no asumas que envuelve todo con el shell del dashboard.
- **Plan comercial como su propio store** (`src/lib/state/plan-store.ts`): `usePlan()`/`setPlan()` sobre el mismo patrón de `localStorage` + `useSyncExternalStore`, independiente de `ProveedorProvider` porque `/registro` (fuera del grupo `(app)`) necesita escribirlo sin montar ese contexto. `ProveedorProvider` lo lee y lo fusiona en `proveedor.plan`. El Topbar tiene un `<select>` de plan pensado solo para explorar la demo (cambia el plan al instante, no es un flujo de cuenta real).
- **Gating por plan** (`src/lib/plan.ts`, `cumplePlan`): matching (badges) y CRM requieren `profesional`+; están gateados en Explorador, Ficha, Dashboard y Oportunidades vía `components/plan/upgrade-notice.tsx` (`UpgradeNotice`/`LockedInline`). El plan `free` además limita resultados visibles (Explorador a 5, "Procesos por vencer" del Dashboard a 2). Si se agrega una función nueva que dependa del plan, seguir este mismo patrón en vez de ocultar cosas ad hoc.
- **Login/registro no validan credenciales**: la contraseña no se verifica contra ningún backend y `/login` no reconoce cuentas — ambos flujos redirigen a `/dashboard` sin autenticación real. Lo que **sí** es real en `/registro` es la búsqueda por RUC contra el RNP del OSCE (ver siguiente sección) y la verificación de correo simulada (genera un código de 6 dígitos y lo muestra en pantalla — no se envía ningún correo de verdad; está rotulado como "modo demo" para no engañar al usuario). Desde esta sesión, `/registro` también exige marcar un checkbox de "Acepto los Términos y Condiciones y el Aviso legal" antes de habilitar "Crear cuenta" (enlaza a `/terminos` y `/legal`).

## Integraciones con fuentes reales del OECE

**Primera integración — RNP del OSCE** (`/registro` pide solo el RUC y llama a `GET /api/rnp?ruc=`, `src/app/api/rnp/route.ts`), proxy server-to-server:

- Endpoint real (no documentado públicamente — se extrajo del bundle JS de `apps.osce.gob.pe/perfilprov-ui`, buscando dónde ese buscador oficial obtiene sus datos): `GET https://eap.oece.gob.pe/perfilprov-bus/1.0/ficha/{ruc}`.
- Confirmado en sesión: responde sin autenticación, sin CAPTCHA, y `robots.txt` de `apps.osce.gob.pe`/`eap.oece.gob.pe` solo bloquea `/cuaderno-obra/` y `/buscador-cuaderno-obra/` (no aplica a este endpoint). `proveedorT01: null` en la respuesta significa "RUC no encontrado", no es un error.
- La respuesta **no** trae header `Access-Control-Allow-Origin`, así que un `fetch` directo desde el navegador seguiría bloqueado por CORS — por eso el proxy tiene que vivir en el backend de Next.js (`/api/rnp`), nunca llamarse directo desde un client component.
- `RnpResultado` (tipo exportado desde `route.ts`, importado como *type-only* en `registro-form.tsx`) siempre distingue `disponible` (¿respondió la fuente?) de `encontrado` (¿existe ese RUC?), para poder degradar visiblemente: RUC no encontrado → formulario manual de razón social; fuente caída → mismo formulario manual con mensaje distinto. Nunca se falla en silencio.
- **Perfil ordenado por tipo de registro** (sesión posterior, a pedido del usuario tras comparar `/perfil` contra la ficha oficial impresa): la respuesta de `ficha/{ruc}` trae `lscIdTipReg` (qué tipos de registro tiene el proveedor — códigos `"1"` Ejecutor de Obras, `"2"` Consultor de Obras, `"3"` Bienes, `"4"` Servicios) y `lscIdTipRegVig`, que antes se descartaban. `EstadoRnp` suma `registros?: RegistroRnp[]` (`{tipo, vigente}`), poblado únicamente desde un fetch real y exitoso — `undefined` si el RNP nunca se consultó con éxito (registro manual o fuente caída), nunca inventado. `rnp-card.tsx` en `/perfil` ya no muestra una lista plana de especialidades: renderiza 4 bloques en orden fijo (Proveedor de Bienes / Proveedor de Servicios / Ejecutor de Obras / Consultor de Obras), solo los que el proveedor realmente tiene, cada uno con badge Vigente/No vigente — `capacidadMaximaGeneral` anidado bajo Ejecutor de Obras y `especialidades` bajo Consultor de Obras, igual que en la ficha oficial. La capacidad de contratación por categoría (autodeclarada por el proveedor, nunca verificada por OSCE) se mudó a su propia tarjeta separada, `capacidad-declarada-card.tsx`, con nota aclaratoria explícita de que no viene del RNP.
  - **`lscIdTipRegVig` tiene la semántica invertida a lo que su nombre sugiere** — encontrado y corregido en esta misma sesión, verificado contra la ficha pública real del RUC de prueba (`https://apps.osce.gob.pe/perfilprov-ui/ficha/20100114187`, confirmado mismo proveedor por CMC "S/ 100,000.00" coincidente): para ese RUC, `lscIdTipReg="3 2 1 4"` y `lscIdTipRegVig="2 1"`, pero la página oficial dice "Vigentes: BIENES, SERVICIOS" y "No vigentes: EJECUTOR DE OBRA, CONSULTOR DE OBRA" — es decir, los códigos que aparecen en `lscIdTipRegVig` (2, 1 = Consultor/Ejecutor de Obras) son justo los que **no** están vigentes, lo opuesto de lo que el nombre del campo sugiere. `parseRegistros()` en `route.ts` usa `vigente: !codigosVigentes.has(codigo)` (negado a propósito, con comentario explicando por qué). El mapeo `3`→Bienes/`4`→Servicios sí se confirmó correcto contra esa misma página.
  - Ningún dato ingresado manualmente (especialidades escritas a mano, `capacidadMaximaGeneral`) desaparece si su registro correspondiente no está presente en `registros` — se muestra como fallback fuera de los bloques en vez de ocultarse, verificado en un perfil real de esta sesión que tenía ambos datos pero `registros: undefined` (registrado antes de este cambio).
  - **Límite conocido de esta sesión**: no se pudo verificar el camino feliz completo (`/registro` con un RUC real → ficha del OSCE responde → `/perfil` muestra los 4 bloques con datos reales) por una caída transitoria del endpoint `eap.oece.gob.pe` durante la verificación (mismo endpoint, confirmado con `curl` directo fallando con connection refused) — no relacionado con este cambio de código. Sí se verificó exhaustivamente por otras vías: la respuesta JSON real capturada anteriormente en el proyecto para el RUC de prueba, el trazado a mano de `parseRegistros()` contra esa respuesta, y visualmente contra el perfil demo (mock) y el caso de registro manual sin RNP.

**Segunda integración — experiencia/contratos del SEACE** (`src/app/api/rnp/experiencia/route.ts`, botón "Importar del SEACE" en `components/perfil/experiencia-card.tsx`):

- Lista: `GET https://eap.oece.gob.pe/perfilprov-bus/1.0/ficha/{ruc}/contrataciones?pageSize=&pageNumber=` (hasta `LIMITE_CONTRATOS = 12`).
- Detalle por contrato (paralelo con `Promise.allSettled`): `GET .../contratacion/{codContProv}/ficha` — trae `fecBaseCont` (fecha real), `provContT01s` (% de consorcio) y, cuando la entidad los publicó, **documentos PDF reales** en `docsContF01.claseDocF01s[].docT01s[].urlDoc` (dominio `eap.oece.gob.pe`, público, sin auth).
- El usuario decide cuáles importar (nunca automático); cada importación queda marcada `fuente: "seace"` en `ExperienciaProveedor` y es editable/eliminable.

**Tercera integración — procesos reales del Portal de Contrataciones Abiertas** (`src/lib/data/live/oece.ts`, API OCDS **oficial, pública y documentada**, Swagger en `https://contratacionesabiertas.oece.gob.pe/api`, distinto dominio/proyecto del RNP). Base: `https://contratacionesabiertas.oece.gob.pe/api/v1`.

- Lista (`buscarProcesosLive`, usada por `listProcesos`): `GET /search?search=&category=&year=&page=&paginateBy=`. El resumen **no** trae dirección estructurada ni documentos — por eso todo proceso de la lista queda con `region: "Otro"` hasta que se abre su ficha. Desde la Décima integración (más abajo), el Explorador enriquece las primeras 15 tarjetas de cada lote con región real vía `/record/{ocid}` — las tarjetas 16+ siguen con "Otro" hasta abrir la ficha.
- Detalle (`obtenerProcesoLive`, usada por `getProceso`): `GET /record/{ocid}`. Ojo con la forma de la respuesta — **no** es `{releases: [...]}` como el endpoint hermano `/release/{id}`, es `{records: [{compiledRelease: {...}}]}`; el dato completo vive en `records[0].compiledRelease`. Los tres documentos reales (bases, buena pro, contrato firmado) están en `compiledRelease.tender.documents[]`, `.awards[].documents[]` y `.contracts[].documents[]`, cada uno con `url` descargable de verdad (dominio `seace.gob.pe`).
- **La dirección (departamento/provincia) no está en `tender.procuringEntity`** — está en `compiledRelease.parties[]`, buscando el `party` cuyo `id` coincide con `buyer.id` (o el que tenga `roles: ["procuringEntity"]`).
- `categoria` en esta fuente solo tiene 3 valores reales (`goods`/`works`/`services` → Bienes/Obra/Servicios); "Consultoría de Obras" es una inferencia heurística (¿el texto dice "consultor"?), no una categoría propia de los datos.
- `tipoProcedimiento` de un proceso live es **texto libre tal cual lo publicó la entidad**, por eso `Proceso.tipoProcedimiento` es `string`, no el union `TipoProcedimiento`.
- Fechas vienen como timestamp ISO completo con hora y zona; `lib/format.ts` (`parseFecha`) maneja ambos formatos — no hacer `new Date(iso + "T00:00:00")` a mano.
- `experienciaMinimaRequerida` y `especialistasRequeridos` no existen en esta fuente: quedan en `0`/`[]`. El matching trata `experienciaMinimaRequerida <= 0` como "no especificado".
- **`fechaLimitePresentacion` NO debe salir de `tender.tenderPeriod.endDate`** — se descubrió (inspeccionando el JSON completo del detalle de dos procesos reales distintos) que para SEACE V3 ese campo **siempre es igual a la fecha de convocatoria**, nunca una fecha límite real. Por eso cualquier proceso recién publicado aparecía "Vencido" el mismo día. El campo real y distinto por proceso es `tender.enquiryPeriod` (ventana de "consultas y observaciones", que sí viene en el detalle aunque no en el resumen de `/search`) — `releaseADetalleProceso` ahora prioriza `enquiryPeriod.endDate` sobre `tenderPeriod.endDate` para `fechaLimitePresentacion`, y el cronograma de la Ficha usa `enquiryPeriod.startDate`/`endDate` como dos etapas reales ("Inicio"/"Fin de consultas y observaciones") en vez del `tenderPeriod` engañoso. **No existe** `awardPeriod`/`contractPeriod` ni un array `milestones` en ningún registro probado — confirmado en dos procesos distintos. La fecha real de cierre de "Registro de participantes" (que si aparece en la ficha visual del SEACE) **no está expuesta por este API en absoluto**; por eso el badge "En plazo de postulación" en `ficha-client.tsx` usa el término genérico "postulación", no "registro" — no se puede garantizar esa fecha específica.
- **Búsqueda por texto/entidad SÍ es server-side de verdad** desde esta sesión (`/api/procesos/buscar`, usado por el Explorador) — ver la integración de año más abajo, que fue el fix real que lo hizo funcionar. Región/monto siguen siendo filtros client-side sobre el batch ya traído.

**Cuarta integración — obras/consultorías acreditadas en el RNP** (`src/app/api/rnp/obras/route.ts`, botón "Importar obras del RNP" en `components/perfil/experiencia-card.tsx`). Es la tarjeta "Acreditada en el RNP" de la ficha de OSCE:

- El endpoint (`expprov-bus`) devolvía error de plataforma cuando le faltaban params — exige TODOS estos, no solo `pageSize`/`pageNumber`: `GET https://eap.oece.gob.pe/expprov-bus/1.0/experiencia/{ruc}/?q=&pageSize=&pageNumber=&t=&vista=1`. `t=1` = "EJECUTOR DE OBRAS", `t=2` = "CONSULTOR DE OBRAS" (viene de `lscIdTipReg` en la ficha del RNP, ej. `"3 2 1 4"`; 3/4 son bienes/servicios, sin tarjeta de obras).
- El código `rnp` que exige el endpoint de documentos **no es un campo de la respuesta** — se extrae de `pathName` (forma `"/RNP/Proveedores/{ruc}/{rnp} EJECUTOR DE OBRAS/.../{codObra}"`). Con eso: `GET .../expprov-bus/1.0/experiencia/{ruc}/{rnp}/{codObra}/?ctx=0` → `documentos[]`.
- Cada documento trae `url` (404, no usar) y `urlEstampa` (el PDF con estampado oficial, dominio `eap.osce.gob.pe` — nótese `osce` no `oece` en este subdominio específico) — usar siempre `urlEstampa`.
- Importación con confirmación del usuario, marcada `fuente: "rnp"` en `ExperienciaProveedor` (union `"manual" | "seace" | "rnp"`). RUC de prueba con datos reales: ICCGSA (20100114187), 5 obras reales.

**Quinta integración — catálogo completo de entidades compradoras** (`src/app/api/entidades/buscar/route.ts`, proxy de `GET https://contratacionesabiertas.oece.gob.pe/api/v1/buyers?buyer=&page=&paginateBy=&format=json`). Es un directorio distinto de `/search` (que lista *procesos*): son las **3,316 entidades registradas** (ministerios, programas adscritos, gobiernos regionales, ~1,874 municipalidades, etc.), cada una con `party.address.department` (región estructurada) y `total_processes` (contador histórico).

- El param `buyer=` SÍ filtra por texto contra el nombre — confirmado con curl (`buyer=PROVIAS` → 3 resultados reales, `buyer=SEDAPAL` → 1). Ojo: **`buyer=` solo funciona en `/buyers`, no en `/search`** — ahí se ignora en silencio y devuelve todo sin filtrar. Otros nombres de param plausibles (`search`, `q`, `name`, `nombre`) tampoco filtran nada en `/buyers`.
- Solo matchea el nombre oficial completo, no siglas sueltas que no aparezcan literalmente (`buyer=PNSR` → 0; hay que buscar "PROGRAMA NACIONAL DE SANEAMIENTO RURAL").
- Usado por: el combobox de "Entidad" del Explorador (`EntitySelect` en `explorador-client.tsx`, a partir de 2 caracteres) y el picker de "Entidades objetivo" en Preferencias del perfil (`EntidadesPicker` en `perfil-client.tsx`) — ambos con el mismo patrón de búsqueda en vivo debounced.
- Al elegir una entidad en el Explorador, su nombre se usa como término para `/api/procesos/buscar` (mismo mecanismo que la búsqueda de texto libre) para traer sus procesos reales, no solo filtrar el lote ya cargado.

**Sexta integración/fix — el filtro `year=` de `/search`, la causa real de "no veo procesos activos"**: una sesión anterior reportó que el Explorador no mostraba ningún proceso vigente incluso filtrando por entidad. La causa **no era un desfase de datos del OECE** (se verificó que el portal actualiza a diario, incluso con entradas literalmente de "hoy") sino que un `search=` de texto libre sin acotar competía contra **~2.7M de registros históricos desde 2003**, y Elasticsearch no prioriza por fecha en ese modo — un proceso recién convocado quedaba enterrado y nunca aparecía dentro del `paginateBy`. El fix: `buscarProcesosLive` (`lib/data/live/oece.ts`) ahora **siempre** manda `year=<año actual>` a `/search` — confirmado con curl que es un param real (`year=2026` reduce `total_results` de ~2.7M a los 41,924 procesos de ese año, que coincide exacto con el contador de la portada del OECE). Verificado end-to-end: buscar "PROVIAS DESCENTRALIZADO" ahora sí trae un proceso convocado 3 días antes de la prueba, que antes era indetectable por la app pese a existir y estar vigente en la fuente.

**Séptima integración — estadísticas de la portada** (`obtenerEstadisticasLive`/`obtenerEstadisticas`, landing page). Mismo endpoint que alimenta los 4 contadores de la portada oficial del OECE (confirmado viendo sus propias peticiones de red): `GET /api/v1/indexCountData?format=json` — no acepta filtro por año pese al nombre; siempre devuelve el desglose completo por año en `years[]`, hay que buscar el año actual ahí mismo. Sin fallback mock (ver nota en "Decisiones de arquitectura").

**Octava integración — procesos por región en el Dashboard** (`obtenerProcesosPorRegionLive`/`obtenerProcesosPorRegion`, `components/dashboard/peru-map-card.tsx`). **No existe un endpoint oficial "procesos por región"** — se revisó el propio Tablero de Procesos de Contratación del portal (`/tableros`) y sus filtros son entidad/año/mes/sistema/categoría/procedimiento/etapa, sin región. Se calcula sumando el catálogo completo de `/api/v1/buyers` (ver quinta integración): cada entidad trae `total_processes` (histórico, todos los años) y `party.address.department` — se suma el primero agrupado por el segundo. Confirmado con curl que ese número coincide con la columna "Procesos" que el propio portal muestra en `/entidades` para esa misma entidad. Con `paginateBy=1000` son solo 4 páginas para las 3,316 entidades; se cachea con `next: { revalidate: 21600 }` (6h) en vez de `no-store` como el resto del archivo, porque es una llamada pesada que no necesita frescura al segundo.

- El contorno de las 25 regiones (`src/lib/data/peru-map.ts`) se generó **una sola vez**, no en runtime: GeoJSON de `juaneladio/peru-geojson` (`peru_departamental_simple.geojson`, licencia MPL 2.0 — atribuida en el comentario del archivo) proyectado con `d3-geo` (`geoMercator`) a paths SVG estáticos. `d3-geo` fue una dependencia de desarrollo temporal (`npm install` → generar → `npm uninstall`), **no** es una dependencia real del proyecto — no debería aparecer en `package.json`. Si hace falta regenerar el mapa (ej. corregir un límite), hay que repetir ese proceso a mano, el script no quedó en el repo.
- La escala de color del mapa es **por ranking**, no por valor lineal — Lima sola concentra ~1.19M de los ~2.7M históricos, así que una escala lineal dejaría casi todo el mapa en blanco.
- El mapa es la "opción 1" de un selector de vistas del Dashboard (`OPCIONES_VISTA` en `peru-map-card.tsx`) con un botón para activar/desactivar — pensado para que agregar una opción 2 (ej. ranking en lista) más adelante sea sumar una entrada al array, no rehacer el componente.

**Novena integración/fix — `montoReferencial`/`montoAdjudicado` nulos, no "S/ 0"**: varios procesos reales mostraban "S/ 0" como valor referencial (ej. `LP-SM-52-2026-ESSALUD/CEABE-1-1`). Confirmado con curl directo a `/api/v1/search` que el OECE publica `"value":{"amount":0.0,...}` **literal**, no un campo ausente/nulo — es la entidad convocante la que no llenó el monto en el SEACE, no un caso "genuinamente cero" (ninguna contratación pública real tiene presupuesto S/0). Por eso `oece.ts` ahora usa `tender.value?.amount || null` (no `?? null`: `0` también debe tratarse como "no publicado", a propósito) y `Proceso.montoReferencial`/`adjudicacion.montoAdjudicado` son `number | null` — `formatMonto()` (`lib/format.ts`) renderiza "No publicado por la entidad" cuando es `null`. Aplicado en Dashboard, Explorador, Comparador, Ranking, Análisis de bases y los exports de Generación de ofertas (docx/excel); `matching.ts` trata el monto nulo como neutral (ni suma ni resta al score).

Antes de replicar este patrón para otra fuente (SUNAT, otro portal), repetir el mismo proceso: revisar `robots.txt`, probar el endpoint real con `curl` server-to-server primero, y documentar el resultado aquí — no asumir que lo que dice el doc de visión (o esta misma sección) sigue vigente sin volver a probarlo.

**Décima integración — ranking histórico, región real en Explorador, perfil de entidad e indicadores de Landing/Dashboard**: surgió de auditar el propio portal del OECE (tableros, docs de Swagger, página de descargas) buscando qué otros datos reales ya expuestos por la fuente no se estaban aprovechando — spec en [`docs/superpowers/specs/2026-07-30-integraciones-oece-avanzadas-design.md`](docs/superpowers/specs/2026-07-30-integraciones-oece-avanzadas-design.md), plan en [`docs/superpowers/plans/2026-07-30-integraciones-oece-avanzadas-plan.md`](docs/superpowers/plans/2026-07-30-integraciones-oece-avanzadas-plan.md). Cuatro mejoras:

1. **Ranking de competidores — vista "Top histórico"**: `/ranking` suma un toggle de vista nueva (la vista existente "Por categoría" vía `/search` se mantiene sin cambios) que trae el top real de proveedores por monto contratado vía `GET /api/v1/contractsSuppliersTop10Dashboard` — agregación server-side real del propio OECE, sin filtro de categoría (el nombre del endpoint es engañoso: no filtra a 10 resultados ni por proveedor individual, es el mismo dashboard agregado que alimenta el tablero público). `obtenerTopProveedoresHistorico` en `oece.ts`, tipo `TopProveedorHistorico`.

## Anexos oficiales de licitación de obras y consultoría de obras (Generación de ofertas)

`src/lib/generacion-ofertas/anexos-obras.ts` genera, prellenados con datos reales del Perfil, los anexos de las **Bases Estándar de Licitación Pública de Obras / Licitación Pública Abreviada de Obras** vigentes bajo la **Ley N° 32069** (no la Ley 30225 — la numeración de anexos cambió entre ambas, no asumir que se mantiene).

- Fuente: Directiva N° 0005-2025-EF/54.01 del MEF (Dirección General de Abastecimiento), modificada por la Resolución Directoral N° 0001-2026-EF/54.01 (https://www.gob.pe/institucion/mef/normas-legales/7614342-001-2026-ef-54-01). Esa página solo enlaza el PDF de la resolución modificatoria (3 páginas, solo aprueba la tabla de 19 tipos de "bases estándar" — no contiene los anexos en sí). El texto completo de los anexos está en los documentos que la resolución manda publicar por separado en `www.gob.pe/mef`:
  - `https://www.mef.gob.pe/contenidos/archivos-descarga/3_Bases_estandar_de_Licitacion_publica_de_obras.docx`
  - `https://www.mef.gob.pe/contenidos/archivos-descarga/4_Bases_estandar_de_Licitacion_publica_abreviada_de_obras.docx`
- **Confirmado extrayendo el texto de ambos .docx** (no asumido): la numeración y el título de los 17 anexos es **idéntica** entre la versión regular y la abreviada — solo cambia el nombre del procedimiento en los encabezados de cada anexo.
- Del propio capítulo "CONTENIDO DE LAS OFERTAS" de las bases estándar (texto oficial, no interpretación): los anexos que se presentan **con la oferta** son el 1, 2, 3, 6 siempre; el 4 solo si es consorcio; el 11 para acreditar experiencia; el 9 y 13 son facultativos/condicionales. Los anexos 7, 8, 10, 12, 14, 16 y 17 están explícitamente marcados en el propio documento como "documento a presentar para el perfeccionamiento del contrato" — es decir, **solo si ganas la buena pro**, no al momento de postular — por eso `generarAnexosObras()` no los genera, solo los lista para que el usuario sepa que existen. El 5 (parentesco con personal de la entidad) y el 15 (reorganización societaria) son casos excepcionales que requieren datos que el sistema no tiene — se listan pero no se autogeneran.
- Gateado por `proceso.categoria === "Obra"` — si el proceso elegido en `/automatizacion` es de otra categoría, se muestra un aviso explícito en vez de generar anexos que no aplican.
- Exporta a Word real (`/api/generar-oferta/anexos-docx`, usa `docx`) y Excel real (`/api/generar-oferta/excel`, usa `exceljs`, nueva dependencia). Los campos que no se pudieron completar con datos del Perfil quedan como `[CONSIGNAR ...]` visibles tanto en la UI como en los archivos exportados — nunca se inventa un valor. El texto introductorio del .docx depende de `proceso.categoria` (Obras vs. Consultoría de Obras), no está hardcodeado a un solo documento.
- El Anexo 11 (experiencia) usa `proveedor.experiencia.filter(e => e.especialidad === "Obra")` — si esa lista está vacía (perfil sin experiencia en Obra registrada), el anexo se genera igual pero lo dice explícitamente en vez de mostrar una tabla vacía sin explicación.

**Extensión a Consultoría de Obras** (sesión posterior, a pedido del usuario tras notar que solo Obra tenía anexos): `src/lib/generacion-ofertas/anexos-consultoria-obras.ts`, archivo hermano de `anexos-obras.ts` (mismo patrón, sin abstracción compartida — el texto oficial y la numeración difieren entre documentos). Este único documento cubre 3 objetos de contratación combinados (Consultorías en general, **Consultoría de Obra**, Servicio de Mantenimiento Vial) en capítulos intercambiables — Urban Procura solo usa la variante Consultoría de Obra.
- **A diferencia de Obras, la numeración NO es idéntica entre el documento regular y el abreviado** — confirmado extrayendo el texto de ambos, no asumido. La versión abreviada tiene un Anexo 17 adicional (bonificación del 5% por condición de MYPE) que la regular no tiene, corriendo el REDAM de Anexo 17 a Anexo 18. Los anexos 1 a 14 (los únicos que usa este generador) sí son idénticos entre ambos documentos.
