# Urban Procura

Visión completa del producto: [docs/prompt-claude-code-urban-procura.md](docs/prompt-claude-code-urban-procura.md). Léelo antes de tomar decisiones de alcance — este archivo solo resume el estado actual y las decisiones de arquitectura ya tomadas.

## Estado actual

Fase 1: **interfaz inicial, sin base de datos ni autenticación real.** El perfil demo y las preferencias/CRM siguen siendo 100% mock/localStorage. Pero **los procesos ya no son solo mock**: el Explorador y la Ficha del proceso consultan en vivo el Portal de Contrataciones Abiertas del OECE (procesos reales del SEACE), y `/registro`/`/perfil` consultan en vivo el RNP y el historial de contratos del OECE por RUC — ver sección "Integraciones con fuentes reales del OECE" más abajo. Cuando una fuente real falla, cada pantalla degrada a datos de muestra **visiblemente** (nunca en silencio) — ver `components/layout/demo-banner.tsx` para el resumen y cada página para el detalle puntual.

Stack: Next.js **15.5.21** (App Router) + React 19 + TypeScript + Tailwind v4. `npm run dev` / `npm run build` / `npm run lint`.

⚠️ **No subir a Next.js 16.x sin probar el deploy primero.** Se usó Next 16.2.11 al inicio del proyecto y tanto Vercel (`vercel build`) como Netlify (`@netlify/plugin-nextjs`) fallaron en producción de formas distintas y difíciles de diagnosticar (ver "Despliegue" más abajo) — aunque el build local funcionaba perfecto. Se bajó a 15.5.21 (última estable al momento) y ambos problemas desaparecieron. Si se vuelve a subir de versión mayor, validar con un deploy real antes de asumir que "compila" = "funciona en producción".

Node no está en el `PATH` de shell por defecto en esta máquina: si un comando `node`/`npm` falla con "command not found", antepón `export PATH="$PATH:/c/Program Files/nodejs"` (bash) o `$env:Path += ";C:\Program Files\nodejs"` (PowerShell) al comando.

## Despliegue

Producción: **https://urban-procura.vercel.app** — proyecto Vercel `urban-procura` bajo el team `urban-procura`, conectado por Git al repo GitHub `lucianoalvarado-spec/urban-procura` (rama `main`). Cada `git push` a `main` dispara un build y deploy automático en la infraestructura de Vercel.

**No usar `vercel deploy`/`netlify deploy` ejecutados directamente desde esta máquina Windows** para desplegar — es la causa raíz de una sesión entera de debugging: el build local en Windows sube a Vercel con una carpeta "src/" duplicada de forma inconsistente y, más grave, hace que `vercel build`/el plugin de Next.js de Netlify produzcan salidas sin rutas registradas (`builds: []`, `NOT_FOUND` en todo, o "Failed publishing static content" en Netlify) — confirmado como un problema específico de Windows (reportado también por terceros en el foro de Netlify). La única forma que funcionó de manera confiable fue conectar Vercel al repo de GitHub (Vercel > Import Git Repository, tras conectar la cuenta de GitHub en vercel.com/account/login-connections) para que el build corra en los servidores Linux de Vercel. Simplemente: **`git push`, no `vercel deploy` local.**

## Decisiones de arquitectura

- **Capa de datos como adaptador reemplazable** (`src/lib/data/provider.ts`): toda la UI llama a `listProcesos`, `getProceso`, `getProveedor`, nunca importa los fixtures ni `lib/data/live/*` directamente. `listProcesos`/`getProceso` intentan el OECE en vivo primero (`lib/data/live/oece.ts`) y caen a los fixtures mock si falla — cada `Proceso` devuelto queda marcado `fuente: "mock" | "live"` (nunca se degrada en silencio: la UI siempre puede distinguir uno de otro). `getDataMode()` sigue devolviendo `"mock"` a propósito — ya no describe fielmente el estado real (los procesos pueden ser live), quedó solo como bandera para el perfil/preferencias que sí son 100% mock; no te fíes de ella para saber si el Explorador está en vivo, mira `proceso.fuente`.
- **Fixtures** en `src/lib/data/mock/` (`procesos.ts`, `proveedor.ts`) — 14 procesos y 1 proveedor demo con datos peruanos realistas pero ficticios. Sirven de fallback cuando el OECE no responde, y de base para el perfil demo cuando nadie se ha registrado.
- **Matching** (`src/lib/data/matching.ts`): heurística explicable por pesos (región, rubro, monto, entidad, palabra clave, tipo de procedimiento, experiencia mínima). Devuelve score + nivel + listas de coincidencias/faltantes explícitas, no solo un número.
- **Estado del lado del cliente** vive en `src/lib/state/`, respaldado por un store minimalista sobre `localStorage` (`local-store.ts`, `createLocalStorageStore`) leído con `useSyncExternalStore` (evita el error de lint `react-hooks/set-state-in-effect` y es hydration-safe: el snapshot de servidor es siempre el default).
  - `proveedor-context.tsx` (`ProveedorProvider`/`useProveedor`): combina `proveedorMock` + `datosEmpresa` (store) + `preferencias` (store) + `plan` (store) en un único `proveedor`. El orden del spread importa: `{...proveedorMock, ...datosEmpresa, preferencias, plan}` — cualquier campo presente en `datosEmpresa` reemplaza al mock; los campos ausentes siguen mostrando el demo (Vientos del Sur) para no romper la experiencia de "solo estoy explorando" sin haberse registrado.
  - `empresa-store.ts` (`useDatosEmpresa`/`setDatosEmpresa`/`updateDatosEmpresa`): `Partial<Proveedor>` persistido, poblado por `/registro` (RUC, razón social, RNP, correo, teléfono, y arrays de experiencia/personal clave/equipamiento/documentos **vacíos explícitamente**, para no heredar los datos de muestra) y editado luego desde `/perfil` vía `actualizarDatosEmpresa` (expuesto por `useProveedor()`).
  - `plan-store.ts` (`usePlan`/`setPlan`): independiente de `ProveedorProvider` a propósito, porque `/registro` vive fuera del grupo `(app)` y necesita escribir el plan sin montar ese contexto.
  - `crm-context.tsx`: estado de seguimiento (`EstadoOportunidad`) por proceso, usado en Explorador, Ficha y `/oportunidades`.
  - Sin backend todavía: esto es persistencia local del navegador, no multiusuario. Cuando exista backend, estos stores deben pasar a leer/escribir vía API en lugar de `localStorage`.
- **Patrón de páginas**: `app/**/page.tsx` es Server Component, hace `await listProcesos()`/etc. y pasa los datos a un Client Component (`*-client.tsx`) que consume los contexts y calcula matching. Mantener este patrón al agregar páginas nuevas.
- **Nav y mapa de módulos**: `src/lib/nav.ts` es la fuente de verdad de qué módulos existen, en qué plan comercial están (`free`/`basico`/`profesional`/`premium`) y cuáles son placeholder (`proximamente`). Los placeholders usan `components/proximamente/proximamente.tsx`.
- **Dos grupos de rutas**: `src/app/(marketing)/` es público (landing `/`, `/login`, `/registro`) con su propio layout (`components/marketing/*`, sin sidebar). `src/app/(app)/` es el dashboard interno (`/dashboard`, `/explorador`, `/procesos/[id]`, `/perfil`, `/oportunidades`, módulos "próximamente") y monta `ProveedorProvider`/`CrmProvider` en su propio `layout.tsx`. El `layout.tsx` raíz solo pone `<html>/<body>` y fuentes — no asumas que envuelve todo con el shell del dashboard.
- **Plan comercial como su propio store** (`src/lib/state/plan-store.ts`): `usePlan()`/`setPlan()` sobre el mismo patrón de `localStorage` + `useSyncExternalStore`, independiente de `ProveedorProvider` porque `/registro` (fuera del grupo `(app)`) necesita escribirlo sin montar ese contexto. `ProveedorProvider` lo lee y lo fusiona en `proveedor.plan`. El Topbar tiene un `<select>` de plan pensado solo para explorar la demo (cambia el plan al instante, no es un flujo de cuenta real).
- **Gating por plan** (`src/lib/plan.ts`, `cumplePlan`): matching (badges) y CRM requieren `profesional`+; están gateados en Explorador, Ficha, Dashboard y Oportunidades vía `components/plan/upgrade-notice.tsx` (`UpgradeNotice`/`LockedInline`). El plan `free` además limita resultados visibles (Explorador a 5, "Procesos por vencer" del Dashboard a 2). Si se agrega una función nueva que dependa del plan, seguir este mismo patrón en vez de ocultar cosas ad hoc.
- **Login/registro no validan credenciales**: la contraseña no se verifica contra ningún backend y `/login` no reconoce cuentas — ambos flujos redirigen a `/dashboard` sin autenticación real. Lo que **sí** es real en `/registro` es la búsqueda por RUC contra el RNP del OSCE (ver siguiente sección) y la verificación de correo simulada (genera un código de 6 dígitos y lo muestra en pantalla — no se envía ningún correo de verdad; está rotulado como "modo demo" para no engañar al usuario).

## Integración RNP (OSCE) — la única fuente de datos real hoy

`/registro` pide solo el RUC y llama a `GET /api/rnp?ruc=` (`src/app/api/rnp/route.ts`), que hace de proxy server-to-server hacia el RNP real del OSCE:

- Endpoint real (no documentado públicamente — se extrajo del bundle JS de `apps.osce.gob.pe/perfilprov-ui`, buscando dónde ese buscador oficial obtiene sus datos): `GET https://eap.oece.gob.pe/perfilprov-bus/1.0/ficha/{ruc}`.
- Confirmado en sesión: responde sin autenticación, sin CAPTCHA, y `robots.txt` de `apps.osce.gob.pe`/`eap.oece.gob.pe` solo bloquea `/cuaderno-obra/` y `/buscador-cuaderno-obra/` (no aplica a este endpoint). `proveedorT01: null` en la respuesta significa "RUC no encontrado", no es un error.
- La respuesta **no** trae header `Access-Control-Allow-Origin`, así que un `fetch` directo desde el navegador seguiría bloqueado por CORS (esto confirma lo que ya sospechaba la sección 3 del doc de visión) — por eso el proxy tiene que vivir en el backend de Next.js (`/api/rnp`), nunca llamarse directo desde un client component.
- `RnpResultado` (tipo exportado desde `route.ts`, importado como *type-only* en `registro-form.tsx`) siempre distingue `disponible` (¿respondió la fuente?) de `encontrado` (¿existe ese RUC?), para poder degradar visiblemente: RUC no encontrado → formulario manual de razón social; fuente caída → mismo formulario manual con mensaje distinto. Nunca se falla en silencio.

**Segunda integración: experiencia/contratos del SEACE** (`src/app/api/rnp/experiencia/route.ts`, usada por el botón "Importar del SEACE" en `components/perfil/experiencia-card.tsx`). Replica el mismo patrón de proxy:

- Lista: `GET https://eap.oece.gob.pe/perfilprov-bus/1.0/ficha/{ruc}/contrataciones?pageSize=&pageNumber=` (hasta `LIMITE_CONTRATOS = 12`).
- Detalle por contrato (llamados en paralelo con `Promise.allSettled`, uno por candidato): `GET .../contratacion/{codContProv}/ficha` — trae `fecBaseCont` (fecha real), `provContT01s` (% de consorcio) y, cuando la entidad los publicó, **documentos PDF reales** en `docsContF01.claseDocF01s[].docT01s[].urlDoc` (dominio `eap.oece.gob.pe`, público, sin auth).
- El usuario ve la lista de contratos candidatos con sus documentos y decide cuáles importar (no se importa nada automáticamente sin confirmación); cada importación queda marcada `fuente: "seace"` en `ExperienciaProveedor` y es editable/eliminable como cualquier otro registro.

**Cuarta integración: obras/consultorías acreditadas en el RNP** (`src/app/api/rnp/obras/route.ts`, usada por el botón "Importar obras del RNP" en `components/perfil/experiencia-card.tsx`). Esta es la tarjeta que en la ficha de OSCE se llama "Acreditada en el RNP" — quedó documentada como no integrada en una sesión anterior porque el endpoint devolvía `"Error en plataforma del servicio"`; se resolvió en esta sesión:

- El problema **no era el endpoint, eran los query params** — el servicio `expprovService` del bundle de `perfilprov-ui` (módulo `oO84`) exige TODOS estos params, no solo `pageSize`/`pageNumber`: `GET https://eap.oece.gob.pe/expprov-bus/1.0/experiencia/{ruc}/?q=&pageSize=&pageNumber=&t=&vista=1`. `t=1` = "EJECUTOR DE OBRAS", `t=2` = "CONSULTOR DE OBRAS" (viene de `lscIdTipReg` en la ficha del RNP, que puede traer varios valores separados por espacio, ej. `"3 2 1 4"`; 3/4 son bienes/servicios y no tienen tarjeta de obras). Confirmado con RUC real 20100114187 (ICCGSA): con los params completos responde `200` con `listaObras[]`, sin params falla igual que antes.
- Cada item de `listaObras[]` trae: `codObra`, `nomObra`/`descObra`, `nomEntCont`, `fecContrato`/`fecCulminacion`, `mtoContrato`, `esConsorcio` (string `"SI"`/`"NO"`, no boolean), `miembrosConsorcio[]` (cada uno `{nomRzsProv: "NOMBRE - XX%"}`, el % viene embebido en el string, no en un campo separado — y el nombre de la propia empresa puede venir abreviado distinto entre registros, así que no se intenta calcular el % propio, solo se listan los miembros en el campo `objeto`), y `pathName`.
- El código `rnp` que exige el endpoint de documentos **no es un campo de la respuesta** — hay que extraerlo de `pathName`, que tiene la forma `"/RNP/Proveedores/{ruc}/{rnp} EJECUTOR DE OBRAS/.../{codObra}"` (ej. rnp `"00931"` para ICCGSA). Con eso: `GET https://eap.oece.gob.pe/expprov-bus/1.0/experiencia/{ruc}/{rnp}/{codObra}/?ctx=0` → `documentos[]`.
- Cada documento trae dos URLs, `url` y `urlEstampa` — **`url` responde 404**, solo `urlEstampa` (el PDF con estampado/sello oficial, dominio `eap.osce.gob.pe`, nótese `osce` no `oece` en este subdominio específico) descarga de verdad. Usar siempre `urlEstampa`.
- Igual que con SEACE, el usuario ve la lista de obras candidatas y decide cuáles importar; cada importación queda marcada `fuente: "rnp"` en `ExperienciaProveedor` (union ahora `"manual" | "seace" | "rnp"` en `src/lib/data/types.ts`) y es editable/eliminable como cualquier otro registro. A diferencia de SEACE, aquí no se guarda `porcentajeParticipacion` (ver punto de arriba sobre por qué no es confiable calcularlo).
- Para encontrar un RUC de prueba con datos reales: no cualquier RUC con `lscIdTipReg` conteniendo "1"/"2" tiene obras (la mayoría de proveedores registrados como ejecutor/consultor de obras no tienen historial) — hay que probar con una constructora real conocida. ICCGSA (RUC 20100114187) tiene 5 obras reales y sirvió para validar todo el flujo end-to-end.
- Antes de replicar este patrón para otra fuente (RNP por nombre, SUNAT, OCDS), repetir el mismo proceso: revisar `robots.txt`, probar el endpoint real con `curl` server-to-server primero, y documentar el resultado aquí — no asumir que lo que dice el doc de visión sigue vigente sin volver a probarlo.

**Tercera integración: procesos reales del Portal de Contrataciones Abiertas** (`src/lib/data/live/oece.ts`, consumida directamente por `provider.ts` — no tiene su propia `/api/*` porque `listProcesos`/`getProceso` ya corren en Server Components, no hace falta un segundo salto). Es una API OCDS **oficial, pública y documentada** (Swagger en `https://contratacionesabiertas.oece.gob.pe/api`, distinto dominio/proyecto del RNP):

- Base: `https://contratacionesabiertas.oece.gob.pe/api/v1`.
- Lista (`buscarProcesosLive`, usada por `listProcesos`): `GET /search?search=&category=&page=&paginateBy=`. Rápida, pero el resumen **no** trae dirección estructurada ni documentos — por eso todo proceso de la lista queda con `region: "Otro"` hasta que se abre su ficha.
- Detalle (`obtenerProcesoLive`, usada por `getProceso`): `GET /record/{ocid}`. Ojo con la forma de la respuesta — **no** es `{releases: [...]}` como el endpoint hermano `/release/{id}`, es `{records: [{compiledRelease: {...}}]}`; el dato completo (tender, awards, contracts, documentos reales) vive en `records[0].compiledRelease`. Los tres documentos reales (bases, buena pro, contrato firmado) están en `compiledRelease.tender.documents[]`, `.awards[].documents[]` y `.contracts[].documents[]` respectivamente, cada uno con `url` descargable de verdad (dominio `seace.gob.pe`).
- **La dirección (departamento/provincia) no está en `tender.procuringEntity`** — está en `compiledRelease.parties[]`, buscando el `party` cuyo `id` coincide con `buyer.id` (o el que tenga `roles: ["procuringEntity"]`). Si se te olvida esto se repite el mismo bug que hubo aquí: región quedaba en "Otro" incluso en el detalle.
- `categoria` en esta fuente solo tiene 3 valores reales (`goods`/`works`/`services` → Bienes/Obra/Servicios); "Consultoría de Obras" es una inferencia heurística (¿el texto dice "consultor"?), no una categoría propia de los datos — puede fallar en casos borde.
- `tipoProcedimiento` de un proceso live es **texto libre tal cual lo publicó la entidad** ("MENOR CUANTIA", "Contratación Directa", etc.), por eso `Proceso.tipoProcedimiento` es `string`, no el union `TipoProcedimiento` (ese union se conserva solo para las preferencias curadas del proveedor). El filtro de tipo de procedimiento en el Explorador ahora se llena con los valores reales presentes en el batch, no con una lista fija.
- Fechas de esta fuente vienen como timestamp ISO completo con hora y zona (`"2026-07-09T10:38:20.843235-05:00"`), no como `"YYYY-MM-DD"` igual que los fixtures. `lib/format.ts` (`parseFecha`) ya maneja ambos formatos — si se agrega una fecha nueva desde cualquier fuente, pasar por esas funciones, no hacer `new Date(iso + "T00:00:00")` a mano (eso rompe con timestamps completos y da `NaN`).
- `experienciaMinimaRequerida` y `especialistasRequeridos` no existen en esta fuente: quedan en `0`/`[]`. El motor de matching (`matching.ts`) trata `experienciaMinimaRequerida <= 0` como "no especificado" y no suma ni resta puntos por eso — no inventar un número ahí.
- No se integró la búsqueda por región/entidad/monto del lado del servidor (aunque el endpoint sí lo soportaría vía más query params) — el filtrado sigue siendo client-side sobre el batch que trae `listProcesos()` (por defecto `paginateBy: 40`, sin filtro). Si el Explorador necesita más volumen o búsqueda server-side de verdad, ese es el siguiente paso natural, no un rediseño.

## Módulos construidos vs. pendientes

Construidos: Landing (`/`), Login (mock)/Registro (RUC→RNP real del OECE, correo con verificación simulada, teléfono, selección de plan), Dashboard, Explorador inteligente (**procesos reales del OECE**, con fallback a muestra), Ficha del proceso (**detalle real con documentos descargables reales**, fallback a muestra), Perfil del proveedor (**totalmente editable**: datos generales, RNP/capacidad, experiencia — incluye importar contratos reales del SEACE y obras/consultorías reales acreditadas en el RNP, ambas con documentos PDF reales —, personal clave, equipamiento, documentos y preferencias — cada sección con su propio componente en `components/perfil/`), Mis oportunidades (CRM) — estos últimos cinco con gating visual por plan.

Placeholder "próximamente" (nav ya existe, pantalla ya explica qué pregunta resolverá, sin lógica real): Alertas, Comparador de procesos, Calendario de plazos, Análisis de bases con IA, Ranking de competidores, Historial de la entidad, Generación de ofertas (roadmap explícito, no MVP).

## Próximos pasos naturales (no implementados)

- Backend real: Postgres + ORM, autenticación (bcrypt/argon2 + sesiones o JWT), storage de archivos. Hoy "crear cuenta" solo guarda en `localStorage` del navegador — no hay multiusuario ni persistencia entre dispositivos.
- Verificación de correo real (envío de código por email) en vez de mostrarlo en pantalla; login que valide credenciales reales.
- Búsqueda server-side de verdad para el Explorador (hoy trae un batch de 40 procesos live y filtra en el cliente) — el endpoint `/search` del OECE soporta más parámetros de los que se usan hoy (`search`, `category` nada más).
- SUNAT vía proveedor de terceros con licencia si de verdad se necesita — nunca automatizar/evadir su captcha (restricción explícita del doc de visión).
- Mover preferencias/CRM/plan/datos de empresa de `localStorage` a persistencia por usuario en backend.
- El gating por plan hoy es solo de UI (cualquiera puede cambiar el `<select>` del Topbar o editar `localStorage`); con backend, la fuente de verdad del plan debe venir del servidor.
